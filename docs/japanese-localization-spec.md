# 日语完整接入与上线规格

状态：待实现。范围已确认，本文不表示翻译、验收或上线已经完成。日期：2026-11-08（America/Los_Angeles）。评估基线：`0daa80d46e77` 及当时工作区中的未提交内容。

交付一个覆盖当前全部公开内容的日语站点：用户可以用日语浏览、检索、理解输入要求、操作模板和查看生成依据。页面与操作说明完整本地化；实际可复制的 Prompt 保留各条目的原始正文及其真实语言。先完成内容、工程和生产产物验收，再启用 `ja`。

本规格面向实现脚本、翻译内容、审校和发布的维护者。基础架构沿用[网站设计第 8 章](prompt-library-website-design.md)、[正文多语言设计](multilingual-prompt-design.md)、[内容维护约定](../content/README.md)和[工程约定](engineering-conventions.md)。本规格补充日语全量上线的检查规则，不改变其他语言按条目独立发布的产品规则。

若准备期间发现已有非原文的日语正文变体，必须在清单中报告其与本次范围的冲突，并显式处理；不得静默删除、覆盖或切换既有内容。其他语言的正文变体继续按原设计工作。

不改 URL 结构、稳定 ID、slug、默认语言或根首页行为；不新增在线生图能力、正文语言选择器或新的翻译状态提示条。其他语言的启用、全量翻译及与日语无关的 SEO 修复另行处理。

6. 每次检查重新读取工作区。正式发布前重新计算新增、变更和移除差集；新增公开内容进入目标，源变更触发复核。

## 3. 本地化完整性规则

| 范围 | 必须覆盖的内容 | 校验方式 |
| --- | --- | --- |
| 界面字典 | 所有 buildable locale 要求的消息；日语必需文本非空 | 对齐默认字典的命名空间、键、ICU 参数，解析语法并审校措辞 |
| 说明页 | 标题、摘要、使用说明、已有独立 SEO 标题／描述 | 既有发布规则加日语覆盖与审校检查 |
| 分类和模板 | 所用术语、分组、字段、枚举标签；已有帮助文字 | 按实际引用逐字段检查，保留稳定参数值 |
| 媒体 | 封面、参考图、结果图、正文配图的语义 alt；已有 caption | 覆盖所有展示的资产，不能只检查封面 |
| 操作和示例 | 已有输入指导、参考图槽位名称、示例观察、图像标注解释 | 从有效输入契约和页面实际展示的运行记录追踪 |
| 合集和专题 | 正文、已有推荐理由、本地化链接目标及成员 | 合集至少 2 个可见成员，专题至少 3 个可见 Prompt，沿用既有阈值 |
| 来源说明 | 已有来源范围、证据方法、来源 Prompt 状态、指标显示名称 | 保留原始数值、日期和链接，仅翻译解释文字 |

源数据不存在的可选信息不要求凭空编写。源语言存在且页面会展示的解释性信息必须有日语版本，缺失时不能靠空字符串、空值或英文回退通过日语发布检查。涉及用户正确操作的必要输入要求即使源说明缺失，也要报告源内容问题。

品牌、模型名称、作者名、URL、技术标识及实际 Prompt 可以保留原文。对其他有意不翻译的文本记录精确字段、理由及审校结果；不使用整份文件或整个目录的宽泛豁免。自动检查可报告疑似原文残留，最终语言质量由审校确定，不能用字符集判断替代审校。

改进后的通用内容规则沿用 `error`、`publish`、`warning`、`info` 四级。日语全量检查额外将目标范围中的缺译、草稿、未审校和过期视为发布阻塞项；其他语言既有的非阻塞警告不因此升级。全局结构错误和发布错误仍然阻止构建。

### 4.2 覆盖检查命令

```bash
npm run locale:check -- --locale ja
npm run locale:check -- --locale ja --strict
npm run locale:check -- --locale ja --strict --json
```

默认命令只读取源文件和审校记录，不写配置、不生成网站、不修改发布状态。普通模式用于准备期间报告缺口；严格模式用于上线检查。

JSON 输出至少包含：`schemaVersion`、`locale`、`sourceRevision`、`scopeFingerprint`、`counts`、`ready`、`items` 和 `findings`。`sourceRevision` 记录 Git commit；`scopeFingerprint` 根据实际源内容计算，确保未提交变更也可识别。每个 item 有稳定 key、来源文件、当前源哈希、目标哈希、页面状态、审核状态和依赖缺口。每个 finding 有稳定规则代码、文件、字段、原因与修复建议。

退出码：`0` 为检查执行成功，严格模式下还要求 `ready: true`；`1` 为结构／发布错误，或严格模式发现日语缺口；`2` 为参数错误。普通模式有缺口时允许退出 `0`，但输出必须是 `ready: false`。`--json` 的 stdout 只含 JSON，诊断写 stderr。输入相同，除时间信息外结果稳定。

准备期 `ja.enabled: false, preview: true`，CI 展示覆盖报告；发布候选显式运行严格模式。正式启用后，日语严格检查成为正常构建与部署的前置条件，使新增公开内容自动进入检查范围。

### 4.3 翻译导入命令

```bash
npm run locale:import -- --locale ja --file translations.json
npm run locale:import -- --locale ja --file translations.json --apply
```

默认只输出将修改的文件、字段与冲突；`--apply` 才写入。输入批次包含 schema 版本、locale、稳定内容 key、明确的源字段／目标字段、预期源哈希、预期目标哈希和译文。目标不存在时以显式空值表示预期不存在，不能省略并解释为任意覆盖。

允许写入的范围仅为目标内容的 `locales/ja.mdx` 和依赖文件内允许的日语文本键。禁止任意文件路径、目录逃逸、修改其他语言、原始 Prompt、模板语义字段、原始生成记录事实或 locale 启用状态。新增示例 `notes.ja` 属于解释性文字，不改变运行正文和生成依据。

写入前重新检查源及目标哈希，拒绝过期批次；取得既有内容写入互斥，暂存整批变更，校验后一次应用。失败时恢复到应用前状态，不能留下半批内容；重复导入相同批次和相同结果为无操作。共享 YAML 只合并目标日语字段，保留其他键和其他工作的修改。

新说明文件默认写为 `draft / machine-draft`。导入不自动标记 `reviewed` 或 `published`，也不接受输入文件以状态字段绕过审校。已公开日语内容的修改先暂存待审，不能直接把线上版本降为草稿；采用审校完成后的内容变更发布。

现有 [content:produce 配方](../scripts/lib/content-production/publish.ts)的页面文案和 alt 限于英／简中。本次通过上述独立导入入口维护日语，避免把翻译任务与生图任务绑定；不要求先改造整个生产配方体系。

## 5. 审校、源变更与文件存储

### 5.1 审校规则

页面说明继续使用现有 `draft | published | archived` 与 `machine-draft | reviewed | outdated`，不增加一套运行时状态。源说明变化沿用现有 `sourceHash` 规则；日语严格检查不接受目标范围内的过期说明。

辅助字段、界面消息、术语和搜索别名的变更另以源／目标指纹检测，覆盖仅改共享 YAML 而不改 MDX 的情况。指纹使用字段路径和规范化内容，不依赖文件修改时间；无关 YAML 键顺序变化不应触发重新审校。页面说明继续使用既有哈希算法，不改变已存哈希格式。

审校记录至少包括稳定范围 key、源指纹、目标指纹、审校者、实际完成时间和结论。范围必须能展开到明确的内容单元或字段集合；修改源或目标中的可翻译内容使相关审校失效。批量审校可以共用一条记录，但必须列出全部项及其指纹，不能只写“全站通过”。

字段不存在的可选项、术语保留原文和其他例外需有具体理由。审校必须检查自然日语、术语一致性、操作含义、来源与许可陈述及图片描述。机器草稿和已有 `reviewed` 标记均不等于本次审校完成；不得代签未发生的审核。

## 6. 翻译执行顺序

1. 先制定术语和写作规范，审校首页、导航、编辑器与错误反馈，确定高频表达，再完成其余消息。
2. 完成术语、字段分组和共享媒体说明；检查现有 24 个标签及新增依赖，不写死标签数量。
3. 翻译全部目标模板的说明、字段、选项显示标签和帮助文字，逐个验证原始默认样例仍可渲染。
4. 按约 25–40 个内容单元一批完成 Prompt。每批同时处理说明、媒体、输入指导、标注与示例，不将关联 YAML 留给最后统一补漏。
5. 完成合集、专题、About 和 License，核对内部链接及全部预期成员。先处理 `about`、`t_001` 的过期说明。
6. 核对 `content/site.yaml` 中首页精选、展出列表和列表穿插项在日语版全部可用，检查真实生产内容量下的首页及分页。

批次按依赖安排，翻译和工程可以分别推进。每批有覆盖报告、审校结果和预览结果；准备期间维持 `ja.enabled: false`，完成的日语文件可标为已审核而继续只在预览中展示。正式启用前不得用机器翻译批量修改发布状态来填平覆盖率。

| JA-08 | 全部目标模板的默认样例与现有样本 | 与原始同版本同参数输出一致，参数约束不变；日语标签不会写进稳定枚举值 |
| JA-09 | 详情、弹层、复制、下载、Markdown、JSON、结构化数据 | 当前正文一致、实际语言正确；原有模型与运行证据保持一致 |
| JA-10 | 模板输入、草稿、分享、重置及切换语言 | 不丢最后一次输入，参数正确恢复；重置使用原始默认样例；复制为最新完整输出 |
| JA-11 | 原文短语与图像标注联动 | 短语和坐标不变，日语解释完整，鼠标、键盘和触屏交互正常 |
| JA-12 | 首页、列表、合集、专题、页脚及正文链接 | 无目标缺页和空的必要入口；合集成员与推荐理由完整；首页编排可用 |

覆盖与导入逻辑使用单元测试及最小真实文件 fixture；全量内容使用 schema、引用和渲染检查；浏览器测试覆盖用户路径。不要用为每段译文复制一份实现逻辑的测试代替审校。

### 7.1 日语搜索与输入法

建立至少 24 条固定查询，覆盖汉字词与复合词、假名、全半角及组合浊点、英文模型名与混合输入、已声明术语别名、完整标题／编号及无结果。每条记录明确的预期资源和通过条件；普通正向查询至少有一个预期资源进入前 5 项，无结果用例必须返回预期空态。

复用现有分词器和索引生成逻辑。平假名、片假名、罗马字或同义词之间的转换仅在明确声明的别名范围验收，不假定当前引擎具有所有语言学能力。样例暴露缺口时先补语料或别名；需要改变分词行为时补跨运行时回归，保持构建端和浏览器一致。

自动化覆盖搜索、快速搜索和模板输入框的 composition：组合期间不提前提交，确认候选后才更新结果；Enter 不误提交，文字与光标不丢失。现有 CDP 日语输入测试只在 Chromium 执行，另需真实日语输入法人工验收桌面和手机主要流程，不能以测试跳过视为通过。

### 7.2 布局、可访问性与性能

使用 Chromium、Firefox、WebKit，覆盖现有 390、768、1024、1440 像素宽度及深浅主题。检查首页、列表、Prompt、模板、合集、专题、搜索、探索、收藏、About、License、缺译和错误状态；无截断、重叠、无意横向滚动、关键控制台错误或 hydration 错误。

键盘操作、焦点恢复、屏幕阅读器标签和图片语义保持有效。日语长标题、长字段帮助、注释及移动操作栏须使用真实译文验收。

全量内容构建后重新测量日语字体子集、重复字体下载、首屏 JavaScript、搜索索引和慢网加载。沿用[首次加载约定](first-load-js.md)与网站设计第 16 章已有预算及已记录例外，不通过下载全部字典或全量 CJK 字体完成接入。发布前提供同条件的前后测量，解释增长来源；上线后的真实用户目标仍为 p75 LCP ≤ 2.5 s、INP ≤ 200 ms、CLS ≤ 0.1，不能用实验室测量冒充真实用户 p75。

## 8. SEO 与生产产物验收

| 项目 | 通过条件 |
| --- | --- |
| 路径和文档语言 | 日语首页 `/ja/`，其他地址沿用稳定 slug；页面 `lang="ja" dir="ltr"`；引用的非日语正文保持自身语言与方向 |

| sitemap | sitemap index 纳入日语 sitemap，列出所有应索引的日语页面和规范分页；草稿、错误页及 noindex 工具页排除 |

| 文本导出 | 日语 Markdown、JSON 和 llms.txt 入口可达，声明与 HTML 的关联正确，原始 Prompt 和许可信息完整 |
| HTTP 和托管 | 根路径生产构建与 `/prompt-seen` 子路径预览构建均通过；重定向、404／410、媒体、数据和字体地址正确 |

全量验证 sitemap 中的地址、canonical 和 hreflang；逐类型检查正文、语言、索引策略及分享信息。核对实际日语索引文档集合与生产可见内容集合，而非仅检查首页存在。复用并扩展现有 `seo.http.spec.ts`、`hosting.http.spec.ts`、`prompt-languages.browser.spec.ts` 和日语输入／布局测试。

## 10. 发布、回滚和持续维护

### 10.1 发布顺序

1. 更新目标差集并完成严格检查；确认所有目标内容审校和测试结果对应当前输入，不复用过期构建结果。
2. 在发布分支准备日语启用提交，将正式启用后的配置纳入验收。不得只测试 `enabled: false` 的预览，然后直接修改开关上线。
3. 对该提交执行完整 CI 和生产产物验收，记录构建版本、测试结果、内容指纹及上一成功部署 ID。合并产生新提交或源输入变化时重新验收。
4. 按[既有部署流程](operations.md)构建与发布，部署前的严格检查对手动部署同样生效。正式产物必须来自通过检查的提交和输入。
5. 执行 `check:live`，额外检查日语 About、License、合集、专题、模板、Prompt、Markdown 及图片；确认正式域名 build ID、索引策略和语言菜单。
6. 检查搜索平台 sitemap 提交状态及既有 IndexNow 流程。搜索引擎实际收录和排名存在延迟，不作为当天发布成功的必要条件。

### 10.2 回滚

广泛 404、模板输出变化、复制失效、严重语言切换或页面错误触发部署回滚。使用现有 Rollback workflow 切回记录的成功版本，随后撤回源代码中的问题提交，避免下一次部署重现问题。

局部翻译问题按内容批次修正或回退，不伪造审校状态。已有日语地址上线后应尽量保持稳定；不能以删除所有日语内容代替局部修复。媒体二进制、Prompt 和历史运行记录在本次发布中不改变。

### 10.3 后续维护

上线当天检查可用性，第 1、7、28 天检查抓取、索引、日语查询、来源流量和移动端表现。按 `/ja/` 区分访问；复制率和搜索成功率只有在相应事件采集实现后才报告，不视为现有分析工具已经提供。

正式启用后的每次发布重新计算日语目标和源变更，严格检查阻止未完成的新增目标或过期内容进入全量日语发布。确需允许语言间短期不同步时，应单独修改并记录发布范围政策，不能悄悄绕过本规格。

语言审校者负责术语与语义，工程维护者负责工具和回归，发布维护者负责候选版本、产物和回滚。角色可以由同一人承担，但不得记录未实际完成的检查或审校。
