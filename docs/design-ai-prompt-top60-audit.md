## 结论

这 60 条可以作为候选清单，不能把原 Markdown 直接导入当前项目。

- **本次导入范围为 58 条图片案例**，前提是把占位符改成项目 Template 字段，准备自有或已授权的参考图，使用最终 Prompt 生成本站样张，再经过媒体、内容和视觉审核。
- **第 15、16 条是图生视频，按本次接入决定移出当前站导入范围**。当前项目的媒体契约只接受 JPEG、PNG、WebP、AVIF，运行记录也只记录图片输出；这两条不生成展示图、不创建内容记录、不加入合集，仅保留为审计排除项。
- **0/60 条可以原样直接发布**。原文件中的方括号字段、中文文案、外部示例图、商标、人物和输入素材都还需要处理；证据等级不等于本站已验证结果，也不自动授予素材复用权。
- 当前项目本身可以承担“生成后入库”的静态流程：`plan → claim → record → review → prepare → apply`。它是预生成的静态内容库，不是用户在网页上上传图片并即时生成的在线服务。

详细的来源与许可核查见 [design-ai-prompt-top60-source-audit.md](./design-ai-prompt-top60-source-audit.md)。

## 对当前项目的核对

当前项目已有以下契约：

- Prompt 可以是 `prompt.txt` 字面文本，也可以通过 `{{fieldName}}` 渲染 Template；原文件的 `[PRODUCT]`、`[城市]`、`{WORD}` 等占位符不能直接作为项目字段。
- `inputRequirements.slots` 可以表达一张或多张参考图，`referenceBindings` 可以冻结上传顺序和角色；这覆盖第 28、37、41–48、49–52、55–56、58 等参考图案例。
- `content:produce` 会保存实际提交的 Prompt、输入哈希、输出哈希、生成方、已知模型信息和人工审核结果；模型没有返回的 provider model ID 应保留未知。
- 媒体 schema 只接受 `image/jpeg`、`image/png`、`image/webp`、`image/avif`，因此第 15、16 不能通过现有媒体和运行记录契约。
- 当前分类词主要是 `product`、`poster`、`illustration`、`architecture`、`food` 等。接入新批次前应补充或确认“信息图、字体/字标、3D 资产、像素/体素、室内”等 taxonomy，否则可以构建但检索和主题页会过于粗糙。

## 生成烟测

为验证“能生成”与“能发布”是两件事，已用当前可用的图像生成工具做了三个代表性烟测，结果未写入 `content/`：

1. 产品白底图（对应 01–04）：主体、材质、留白和柔影可生成，适合作为待审核样张。
2. 参考图材质重做（对应 52）：主体球体和内部场景大体保留，但折射、高光和水流颜色明显变化，说明仍需视觉验收。
3. 中文信息图（对应 37）：短标题和四个指定标签可读，但模型额外生成了未要求的说明文字；“中文无乱码/精确文本”不能作为自动保证，生产图应后期排版或逐字验收。

这三个烟测证明当前工具能够产出候选图片，不能替代 58 条逐例生成、输入准备、授权检查和发布审核。

## 推荐接入顺序

1. 先接入 01–14、17–20、27、29、36、49、52、54、57、59 等低输入复杂度案例，统一改成 Template 并验证字段约束。
2. 再接入 21–26、30–40、53、60，把文本、事实、商标和品牌字段作为人工审核项；重要文案优先后期排版。
3. 最后接入 28、37、41–48、50–51、55–56、58，准备原创/授权参考图并记录槽位绑定；第 42 条拆成两次有序运行。
4. 第 15、16 不进入本批导入、生成或合集；若未来要发布，需新增视频媒体类型、播放器/缩略图、转码、存储和视频验收契约后单独评估。

发布前每条都应满足：最终 Prompt 与生成回执一致、输入素材权利明确、样张通过构图/主体/文字/事实检查、`content:validate` 无错误，并明确是 draft 还是 published。
