The retained full-suite and isolated-retry failures waited for the native new-tab `page` event, before checking the document or no-JavaScript branch. DOM instrumentation recorded `metaKey=true`, `button=0`, `isTrusted=true`, `defaultPrevented=false`; the gallery address remained unchanged and no application popup opened. Thus the failure is not the popup interceptor swallowing the click or malformed subpath navigation.

A control with the same target/native context opened the expected tab. Different modifier and user-agent controls ruled out a consistent incorrect key or UA-specific product behavior. Minimal plain-link probes could also exhibit absent native tabs, supporting a browser/environment boundary. The original unchanged test subsequently passed once (13.3s), so the failure is intermittent, not claimed to be every-run deterministic. Headless Firefox reports both tab documents focused/visible in a two-tab probe, so DOM `hasFocus` is not proof of OS-window activation.

Selecting the originating gallery explicitly with `page.bringToFront()` before the trusted modified click produced three successful isolated exact-device contexts. The narrow test change requests the user's native interaction precondition; it cannot reserve the foreground window against another worker. It retains every original assertion, modifier, new-tab event, destination text, original-gallery/no-popup check and no-JavaScript navigation. No skip, retry-until-pass, timeout increase or replacement synthetic `window.open` was introduced. The existing `tab.bringToFront()` after opening remains.

Why this test: ordinary locator clicks assert app DOM event handling. This scenario additionally delegates tab creation to Firefox's native chrome/platform behavior, where the observed delays and failures can occur even when content receives trusted mouse events. Originating-window activation was an early hypothesis, not a sufficient root cause. Explicit foreground selection belongs immediately before that native action; it is not a reason to add foreground calls to all app controls. The follow-up protocol observations refine this boundary; the exact cause of the original timeout remains unproved.
